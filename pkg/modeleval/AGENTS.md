# pkg/modeleval — agent notes

Native Go implementation of the MCP `eval_model_on_split` and
`compare_models` tools. Replaces the `python3 -c` helper that
`cmd/vmafx-mcp/impl.go` used to shell out to (ADR-0704 Stage 2).

Reference implementation being ported:
`mcp-server/vmaf-mcp/src/vmaf_mcp/server.py::_eval_model_on_split` /
`_compare_models`.

## Load-bearing invariants

1. **The split hash is frozen.** `split.go` must keep producing
   `sha256("vmaf-train-splits-v1:" + key)`, first 8 bytes big-endian,
   divided by 2^64, with the `test < 0.1 <= val < 0.2 <= train`
   comparison chain in that order. It matches `vmaf_train`'s
   `split_keys` and the Python MCP server. Any drift silently
   re-partitions every cached feature table and invalidates
   cross-language model comparisons. `split_test.go` asserts
   **bit-equality** against values generated by the Python original —
   those are not tolerance assertions, do not loosen them.

2. **Feature-column order is the model's input contract.**
   `FeatureColumns` is the canonical order (`adm2`, `vif_scale0..3`,
   `motion2`); columns absent from the table are skipped and the
   survivors keep this relative order. The ONNX graph is fed a
   `[rows, len(cols)]` tensor in exactly this layout, so reordering
   the slice silently feeds the model transposed features.

3. **`Result` field order is the wire format.** The MCP layer
   serialises handler results with `json.MarshalIndent`, so struct
   field order *is* JSON key order. The order mirrors the Python
   dict's insertion order; `TestResultJSONKeyOrder` pins it.

4. **Statistics run in float64, Python's run in float32.** scipy does
   not upcast the float32 arrays the Python server hands it, so the two
   implementations agree to ~1e-7 on PLCC, ~1e-9 on RMSE, and exactly
   on SROCC (rank-based). This is a documented, deliberate divergence —
   see the package comment in `stats.go`. Do not "fix" a diff at that
   magnitude by reproducing numpy's float32 accumulation.

5. **Non-finite results are errors, not NaN.** `encoding/json` cannot
   marshal NaN, so a degenerate (zero-variance) input must fail loudly
   rather than propagate. Deliberate divergence from Python, which
   emits an invalid bare `NaN`.

## Generating goldens

The scipy goldens in `stats_test.go` and `eval_test.go` were produced
with scipy 1.18.1 / numpy 2.5.2. When regenerating from a Go-side dump,
parse the JSON as **float32 first** and then widen: Go writes the
shortest decimal that round-trips as float32, so reading it straight
into float64 yields a subtly different number and shifts PLCC by ~1e-8.

## ONNX inference lives elsewhere

The forward pass is behind the `Predictor` interface so this package
stays pure Go and testable with `CGO_ENABLED=0`. The production
implementation is `pkg/libvmaf.DNNSession` (cgo), which binds libvmaf's
`vmaf_dnn_session_*` API. Deliberately **no** third-party Go ONNX
dependency: libvmaf already links ONNX Runtime and applies the model
size cap and operator allowlist (ADR-0211).

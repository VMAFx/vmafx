# ADR-3557: Queue same-head pull-request runs on merge-gate workflows

- **Status**: Accepted
- **Date**: 2026-11-17
- **Deciders**: Project maintainer
- **Tags**: ci, fork-local

## Context

The `master` ruleset requires one status-check context: `Required Checks Aggregator` (`.github/workflows/required-aggregator.yml`, job `aggregator`, [ADR-0313](0313-ci-required-checks-aggregator.md)). GitHub evaluates branch protection across the latest check run of every check suite on the head commit, so a `cancelled` `Required Checks Aggregator` run in one check suite keeps the pull request `BLOCKED` even when a sibling suite on the same head passes (pull request 3445 rollup: `CANCELLED` at `01:35:32Z` plus `SUCCESS` at `01:48:19Z`, rollup state `FAILURE`).

Since [ADR-3551](3551-aggregator-edited-window.md), `required-aggregator.yml` triggers on `[opened, edited, synchronize, reopened, ready_for_review]` with `group: required-aggregator-${{ github.workflow }}-${{ github.ref == 'refs/heads/master' && github.sha || github.ref }}` and `cancel-in-progress: ${{ github.ref != 'refs/heads/master' }}`. A review bot edits the pull-request body 7-10 seconds after each push (`pull_request` action `edited`), so the `edited` run cancels the running push run of the same head (observed on pull requests 3434, 3445, 3456, 3505, 3510, and 3522 on 2026-11-17). `.github/workflows/rule-enforcement.yml` (`Rules`) has the same defect: its triggers include `edited` with `group: rule-enforcement-${{ github.event.pull_request.number }}` and `cancel-in-progress: true`, while on `edited` the aggregator correlates `editedRerunWorkflows` by the `"[<pull_request.updated_at>] "` `display_title` prefix and fails when that `Rules` run's jobs are cancelled (pull request 3456, aggregator run `43996540618` attempt 3: nine `Rules` jobs cancelled, aggregator failed); re-running one twin cancels the other.

Keeping one pull-request concurrency group on `rule-enforcement.yml` also leaves a two-edit pending-replacement defect (PR 3529 review). Under GitHub Actions concurrency (`github/docs` `data/reusables/actions/actions-group-concurrency.md`, commit `336b7f546d`), a concurrency group holds at most one running and one pending run, and queuing a new run cancels the existing pending run in the group even when `cancel-in-progress` is false. When edit A starts aggregator A while an earlier `Rules` run holds the group, `Rules` A waits as pending; edit B then queues `Rules` B and cancels pending `Rules` A with zero jobs, so aggregator A finds only a cancelled `Rules` run bearing its `"[<pull_request.updated_at>] "` stamp, its `Rules` check runs never register, and aggregator A fails at its 2-minute registration grace deadline, leaving a failed `Required Checks Aggregator` suite on the head commit that keeps the pull request `BLOCKED` even after aggregator B passes.

## Decision

Enable `cancel-in-progress` only for `synchronize` pull-request events in both merge-gate workflows, keep the aggregator concurrency `group:` unchanged, and give each `edited` run of `.github/workflows/rule-enforcement.yml` its own concurrency group keyed on `github.run_id`:

- In `.github/workflows/required-aggregator.yml`, set `cancel-in-progress: ${{ github.event_name == 'pull_request' && github.event.action == 'synchronize' }}`, leaving triggers, `permissions:`, `group:`, and the embedded `script:` block unchanged.
- In `.github/workflows/rule-enforcement.yml`, set `group: rule-enforcement-${{ github.event.pull_request.number }}-${{ github.event.action == 'edited' && github.run_id || 'head' }}` and `cancel-in-progress: ${{ github.event.action == 'synchronize' }}`, leaving triggers, `permissions:`, and `run-name` (`"[${{ github.event.pull_request.updated_at }}] ${{ github.event.pull_request.title }}"`) unchanged while the aggregator concurrency `group:` stays unchanged.
- Under GitHub Actions concurrency (at most one running and one pending run per group), a `synchronize` push to a new head still cancels the stale running run in the pull-request group, while same-head `edited`, `reopened`, and `ready_for_review` aggregator runs wait as pending and repeated pending aggregator runs collapse to the newest (`release-please.yml` runs `37229262831` and `37230781106` end `cancelled` with zero jobs and zero check runs when replaced while pending). On `rule-enforcement.yml`, each `edited` run gets its own group keyed on `github.run_id` (unique per workflow run), so no later edit (same second or not) or other same-head event replaces or cancels it; `run-name` keeps the `"[<pull_request.updated_at>] "` stamp for aggregator correlation, and same-second edits sharing that stamp fail closed as ambiguous in `required-aggregator.yml` ([ADR-3551](3551-aggregator-edited-window.md)), while non-`edited` events share the `-head` group. Leave the 24 other pull-request workflows unchanged: none reports a required context directly on branch protection, and the aggregator's `newestByName` selection picks their surviving newer twin.
- Extend `scripts/ci/tests/test_master_concurrency_contract.py` (`pr_push` and `pr_event` with `updated_at` and optional `run_id`, `gate_workflows`, `same_head_findings`, `pending_replacement_findings`, `skip_findings`) so the gate workflow set (`required-aggregator.yml` plus basenames in `editedRerunWorkflows`, failing on a missing or empty array) forbids same-head cancellation on every non-`synchronize` (`!= 'opened'`, `!= 'closed'`) `pull_request` type with a distinct `run_id` at `T1` and `T2` compared against every running `pull_request` type of the workflow at `T1` (including `synchronize` and the incoming action itself) at workflow and job level, forbids any non-aggregator gate workflow with `edited` in `pull_request.types` from sharing an `edited` run's concurrency group (`T1`, `run-edit-1`) with a later same-head `pull_request` action carrying a distinct `run_id` at `T1` (same second) or `T2` (`pending_replacement_findings`), verifies `synchronize` across distinct SHAs still shares a group with `cancel-in-progress` true, and forbids any `if:` on `jobs.aggregator` or step-level `if:` in that job mentioning `github.event.action` or `edited`.

## Alternatives considered

| Option | Pros | Cons | Why not chosen |
| --- | --- | --- | --- |
| Option a: keep existing `group:` and set `cancel-in-progress` true only on `pull_request` `synchronize` | Preserves master SHA isolation and new-head superseding; same-head `edited`, `reopened`, and `ready_for_review` aggregator runs wait as pending and collapse to the newest with zero check runs on replaced pending suites | Same-head `edited` aggregator twin waits for the running push run to finish; re-running a `synchronize` run while an `edited` twin runs cancels the twin; on `rule-enforcement.yml` alone, a second edit replaces a pending `Rules` run and fails the first edit's aggregator | Chosen for `required-aggregator.yml` (paired with Option h on `rule-enforcement.yml`) |
| Option b: head-SHA concurrency group with `cancel-in-progress: true` | Separates distinct commits into distinct concurrency groups | A same-head `edited`, `reopened`, or `ready_for_review` event shares the head SHA and still cancels the same-head twin, while a push to a new head no longer cancels the older head's run | Rejected: still cancels the same-head twin |
| Option c: `concurrency.queue: max` | Declares queueing explicitly in workflow YAML | The pinned `actionlint` v1.7.12 in `.pre-commit-config.yaml` refuses it (`unexpected key "queue" for "concurrency" section`), and it cannot combine with `cancel-in-progress` | Rejected: `actionlint` 1.7.12 refuses `queue`, and it cannot combine with `cancel-in-progress` |
| Option d: job-level `if:` skipping `jobs.aggregator` on `edited` | Starts no second aggregator job on pull-request edits | Branch protection counts a `skipped` required status check as passing, which masks a failed or pending aggregator run on the same head | Rejected: `skipped` counts as passing and masks a failed run |
| Option e: per-head-SHA group without cancel plus an in-script supersede check | Avoids Actions concurrency cancellation between same-head suites | A `synchronize` push to a new head no longer cancels the stale run natively (holding runner slots until script polling notices) and adds extra GitHub API calls on every poll | Rejected: new heads no longer cancel stale runs natively, and polling adds extra API calls |
| Option f: `queue: max` on `rule-enforcement.yml` with `cancel-in-progress: ${{ github.event.action == 'synchronize' }}` | Keeps up to 100 pending `Rules` runs in one group without replacing earlier edits | Combining `queue: max` with `cancel-in-progress: true` (when `synchronize` evaluates true) is a GitHub Actions workflow validation error (`github/docs` `data/reusables/actions/actions-group-concurrency.md`, commit `336b7f546d`) | Rejected: validation error with `cancel-in-progress: true` on `synchronize` |
| Option g: per-edit `updated_at` group on `rule-enforcement.yml` (`rule-enforcement-<number>-<stamp>`, where the stamp is `pull_request.updated_at` on `edited` and `head` on every other action) with `cancel-in-progress: ${{ github.event.action == 'synchronize' }}` | Gives edits stamped in distinct seconds separate concurrency groups matching the `run-name` edit stamp while non-`edited` events share the `-head` group and `synchronize` cancels stale head runs | `pull_request.updated_at` has one-second resolution, so two edits in the same second share one concurrency group and the second edit replaces a pending first edit's `Rules` run; a `synchronize` push also no longer cancels an old-head `edited` `Rules` run | Rejected: one-second `updated_at` resolution still lets same-second edits share one group and replace a pending `Rules` run |
| Option h: per-edit `github.run_id` group on `rule-enforcement.yml` (`rule-enforcement-<number>-<key>`, where the key is `github.run_id` on `edited` and `head` on every other action) with `cancel-in-progress: ${{ github.event.action == 'synchronize' }}` | `github.run_id` is unique per workflow run, so no two `edited` runs ever share a concurrency group (including edits stamped in the same second), while `run-name` keeps `pull_request.updated_at` for aggregator correlation and non-`edited` events share the `-head` group | A `synchronize` push no longer cancels an old-head `edited` `Rules` run; same-second edits still share the `updated_at` prefix in `run-name`, where the aggregator fails closed as ambiguous per ADR-3551 | Chosen for `rule-enforcement.yml` |

## Consequences

- **Positive**: same-head `edited`, `reopened`, and `ready_for_review` events (including automated review-bot body edits seconds after a push) no longer cancel a running `Required Checks Aggregator` or `Rules` run of the same head; repeated pending aggregator edits collapse to the newest pending run with zero check runs on replaced pending suites; each `edited` `Rules` run keeps its own `github.run_id` concurrency group so no later edit (same second or not) replaces or cancels it, while `run-name` keeps the `updated_at` stamp and same-second edits sharing that stamp fail closed in the aggregator ([ADR-3551](3551-aggregator-edited-window.md)); `synchronize` pushes to a new head still cancel superseded head-group runs immediately; master push SHA isolation ([ADR-1673](1673-master-runs-not-cancelled-by-concurrency.md)) holds unchanged.
- **Negative**: a same-head `edited` run of `required-aggregator.yml` (or a same-head `reopened` / `ready_for_review` run of `rule-enforcement.yml`) waits in `pending` until the running push run finishes. A `synchronize` push to a new head no longer cancels an old-head `edited` `Rules` run (it runs to completion on the old head; the aggregator filters runs by head SHA). Same-second edits share one `pull_request.updated_at` stamp in `run-name`, so `required-aggregator.yml` fails closed on the ambiguous stamp ([ADR-3551](3551-aggregator-edited-window.md)). Residual risk: manually re-running a same-head `synchronize` run while its `edited` aggregator twin is running evaluates `github.event.action == 'synchronize'` to true and cancels the running `edited` aggregator twin (`docs/development/ci.md` instructs operators to re-run a cancelled aggregator only when no aggregator run of the same head is in progress).
- **Neutral / follow-ups**: open question (present since [ADR-3551](3551-aggregator-edited-window.md)): because GitHub counts the latest check run of every check suite on the head commit, an earlier failed `Required Checks Aggregator` suite on the same head stays red on the commit rollup even after a passing `edited` aggregator run until the failed suite itself is re-run or a new commit is pushed. `scripts/ci/tests/test_master_concurrency_contract.py` enforces same-head queueing, pending-edit isolation including same-second edits (`pending_replacement_findings`), new-head superseding, `editedRerunWorkflows` discovery, and the no-skip rule across repository and synthetic workflows.
